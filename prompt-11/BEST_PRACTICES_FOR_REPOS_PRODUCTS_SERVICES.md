# Prompt #11 Best Practices for Repositories, Products, Services, Projects, and Platforms

This guide defines best practices for all lippytm.AI repositories and business systems connected to Prompt #11.

## Universal Best Practices

Every repo, product, service, project, or platform should have:

- clear purpose
- owner
- lane
- target audience
- current status
- next action
- quality standard
- risk level
- documentation
- acceptance criteria for changes
- maintenance review path
- improvement loop

## Repository Best Practices

Each repository should include:

```text
README.md
PROJECT.md
QUALITY.md
RISK_GATE.md
AGENT_MODE.md
PROMPT_11_NODE.md
.github/ISSUE_TEMPLATE/
.github/workflows/
```

Recommended repo rules:

- Keep README simple and current.
- Use GitHub issues for work tracking.
- Use PRs for meaningful changes.
- Keep PRs small.
- Use labels for status, lane, risk, and type.
- Document validation steps.
- Do not mix unrelated changes.
- Update dashboards after important changes.

## Product Best Practices

```yaml

  name: null
```

Product checklist:

- clear offer
- clear buyer/user
- clear deliverable
- simple setup
- proof or demo
- support instructions
- disclaimers where needed
- checkout/delivery flow
- feedback loop

- service name
- outcome delivered
- setup requirements

- onboarding steps
- communication channel
- delivery checklist

Service examples:

## Platform Best Practices

Each platform should define:

- platform purpose
- user journey
- primary CTA
- integrations
- data collected

- revenue pathway
- maintenance owner
- dashboard metrics

## Creative Solutions Best Practices

Creative projects should use the Transparent Worlds separation doctrine:

- real business
- education
- documentary/commentary
- fiction/satire
- music/film/art
- experimental research and development
- advertisement/offer
- affiliate/partner mention

Rule:

```text
Creative connection is allowed. Category confusion is not.
```

## AI Engine Best Practices

Every AI Engine should declare:

- active Prompt #11 engines
- allowed work
- restricted work
- human approval triggers
- quality requirements
- awareness fields
- next action

## Product-Service-Repo Alignment

Every product or service should map to at least one repo or durable documentation location.

```yaml
alignment:
  offer: Example Offer
  repo: lippytm/example-repo
  docs: path/to/docs
  dashboard: path/to/dashboard
  support_channel: null
  next_action: null
```

## Principle

The best practice is not to build everything at once. The best practice is to build the smallest useful version, document it, test it, package it, and improve from evidence.
